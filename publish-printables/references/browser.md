# Printables setup and reusable editor map

The live site requires Prusa Account sign-in. No supported public upload API was verified, and the site's GraphQL endpoint rejects schema introspection. The Python adapter uses Playwright's documented [Python locator](https://playwright.dev/python/docs/locators) and [file upload](https://playwright.dev/python/docs/input#upload-files) interfaces. It does not reverse-engineer tokens or replay undocumented GraphQL mutations.

From this skill directory:

```bash
uv sync --locked
uv run --locked playwright install chromium
uv run --locked scripts/upload_printables.py login --profile-dir /private/credentials/printables-profile
uv run --locked scripts/upload_printables.py inspect --profile-dir /private/credentials/printables-profile
```

Use a dedicated directory outside the repository/vault. The user completes sign-in and any service checkpoint. The saved profile can contain session cookies, so treat it as a credential. A regular run is headless; `--headed` opens the browser for troubleshooting. Nothing takes screenshots, exports cookies, or inspects other browser profiles.

The first signed-in editor inspection must produce a reusable JSON map. The map is site configuration, not listing content. It should be generated by the agent from inspected controls, saved outside the repository as local configuration, and reused on later uploads. No live map is bundled: the editor was behind sign-in during development. Do not claim this adapter is ready for unattended live posting until that mapping and a draft smoke test have passed.

Map schema:

- `schema`: `1`; `category`: the chosen category name; `license`: the manifest licence code.
- `fields`: locators for `title`, `summary`, `description`, `tags`. Text inputs and contenteditable fields are supported. The description is entered as plain text with its existing Markdown headings; saved text is checked, not rich-text styling.
- `choices`: category/licence selection steps. Each has `field` (`category` or `license`), `locator`, `option_label` for a native select, `check: true` for a checkbox/radio, or neither for a click. Each also has `verify`, plus `expected` (saved value) or `checked: true`. A custom dropdown can use several click steps sharing the final verification locator.
- `uploads`: file-input locators keyed by `file`, `image`, and, when present, `print_file`. Inputs may be hidden. Uploads are grouped, not clicked through file dialogs.
- `uploaded_items`: locators with the same keys, selecting elements whose text is exactly the uploaded filename. Add `name_attribute` when filenames are in `title`, `alt`, or another inspected attribute.
- `tag_items`: a locator selecting only tag labels, excluding removal controls. Printables tags are lowercased and spaces become hyphens so phrases are submitted as one value.
- `save_draft`: the actual save control, whose visible text or accessible label must explicitly contain “draft”. Public/publish controls are rejected.
- `draft_marker`: an inspected visible marker proving the saved detail page is a draft.
- `reopen_editor_url`: optionally override the default `https://www.printables.com/model/{id}/edit` with the inspected editor URL pattern.
- `slicing_checks`: when the manifest records slicing, a list of `profile_key` and `locator` pairs. Each must select the detected value matching that recorded profile value.

A locator uses exactly one of `{"label":"observed label"}`, `{"role":"button","name":"observed name"}`, `{"placeholder":"observed placeholder"}`, `{"text":"observed text"}`, or `{"css":"observed selector"}`. Native select verification compares its saved value; use the actual inspected option value for `expected`.

After mapping:

```bash
uv run --locked scripts/upload_printables.py --manifest /absolute/release/release-manifest.json --ui-map /private/settings/printables-map.json
uv run --locked scripts/upload_printables.py --manifest /absolute/release/release-manifest.json --ui-map /private/settings/printables-map.json --profile-dir /private/credentials/printables-profile --execute
```

On a failed upload/save, retain `.publication-state/printables.json`. Find the existing draft using a focused inspection; then `--resume-url <draft-url>` verifies it without uploading the files again. If verification finds missing content, reconcile that draft before attempting another save. An ordinary successful rerun only reopens and verifies the recorded draft.
